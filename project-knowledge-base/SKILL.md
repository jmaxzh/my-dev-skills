# 文档规范

## 写作风格

- 使用电报体。按字收费。准确、简洁。删掉每个不必要的词。
- 使用祈使句。写“配置 X”。不要写“你需要配置 X”。
- 先识别目标读者：产品使用者、产品维护者等。
- 默认优先服务产品使用者。主要服务维护者时，按维护者的任务和认知方式组织内容。
- 使用读者可感知的示例说明功能。不要使用内部实现术语解释行为。
- 使用：“在聊天输入框粘贴图片即可发送”。
- 不要使用：“`ChatInput` 组件监听 `paste` 事件，将 `File` 转为 `dataUrl`，再传入 `appendOptimisticTurn`”。

## 文档职责

- 让每篇文档只承担一种 Diátaxis 职责。

| 类型            | 导向 | 回答                 | 示例                  |
| --------------- | ---- | -------------------- | --------------------- |
| **Tutorial**    | 学习 | 怎么上手？           | 新手引导、Quick Start |
| **How-to**      | 任务 | 怎么完成 X？         | 操作步骤、配置指南    |
| **Reference**   | 信息 | X 的精确规格是什么？ | API 参考、配置项清单  |
| **Explanation** | 理解 | 为什么这样设计？     | 当前架构原理、稳定权衡 |

- 选择一种类型。不要混合职责。
- 使用交叉链接补充其他类型的信息。不要内嵌。
- 仅为涉及系统架构、当前设计原理或稳定权衡的 Explanation 按需使用 arc42。
- 将 arc42 仅用于组织单篇架构文档。不要用它决定文档类型、目录结构或文件名。
- 按需选择 arc42 章节：Introduction & Goals、Constraints、Scope、Solution Strategy、Building Block、Runtime、Deployment、Cross-cutting、Quality、Risks、Glossary。

## 命名规范

- 使用文件名前缀标识 Diátaxis 类型。
- 使用 `tutorial-` 标识 Tutorial。
- 使用 `howto-` 标识 How-to。
- 使用 `ref-` 标识 Reference。
- 使用 `expl-` 标识 Explanation。
- 按领域或功能组织目录。不要镜像代码模块。
- 在同一领域目录内放置不同类型的文档。使用前缀区分类型。

## 组织规范

- 按领域或功能聚合文档。
- 集中存放同一领域、功能或模块的文档。
- 使用交叉链接关联不同领域。
- 不要照搬代码的 `hooks/`、`components/`、`lib/` 等目录结构。
- 让每个文件只承载一个主题。
- 将每个文件控制在 500 行非空行以内。
- 将每个目录的 Markdown 文件控制在 8 个以内，包含 `index.md`。超限时拆分子目录。
- 仅在 `index.md` 中提供概览、快速开始和核心导航。不要承载细节。
- 使用唯一导航清单定义层级与可见性。注册每个新增页面。
- 在 `APP_ROOT` 内验证路径、命令、接口、配置和行为。

## 格式规范

- 添加 YAML frontmatter。
- 填写非空 `title`。
- 按需填写 `summary` 和 `read_when`。
- 为代码块标注语言。
- 使用段落和纯列表组织正文。
- 不要使用表格。仅保留 Diátaxis 分类示意表。
- 按需使用图表和截图。
- 不要为标题添加数字前缀。
- 仅在步骤存在顺序时使用有序列表。

## 实施状态

- 为每份文档标注 `规划` 或 `已实现`。
- 在对应章节标题下标注状态。
- 拆分混合状态的章节。
- 不要将规划内容写成现有能力。

## 内容边界

- 只将当前、可复用、需长期维护的知识写入 `docs/`。
- 写入前确认：当前有效、未来需要、归属明确。任一不满足，不落地。
- 优先更新权威文档。主题独立且无法归入既有文档时，才新建页面。
- 将访谈、对话、Plan、评审、Git 提交、diff、历史、弃选方案和推导过程仅作参考。
- 不要落地参考材料。不要转存为决策记录、ADR、评审文档、Plan 或其他文件。
- 将“关键决策”提炼为当前规则或约束。省略过程、人员、时间、提交、历史和弃选方案。
- 记录稳定的“为什么”和当前的“是什么”。只保留理解当前设计所需的长期因果关系。
- 记录用户可感知需求、架构意图、边界、不变量、当前规则和稳定权衡。
- 记录任务目标、必要操作路径、公共 API、命令和配置的用法。
- 将精确签名、Schema、默认值和完整取值范围留给代码或专用契约。
- 在文档中引用规范性定义，或提供非穷举示例。
- 为每个事实只保留一个规范性定义。
- 在其他文档中交叉链接该定义。不要重复定义。
- 将实现结构和执行行为留给代码。
- 引用外部协议的官方规范。
- 删除、抽象或引用易变的内部实现细节。
- 不要记录内部组件、函数、类型、helper 和字段名。
- 不要记录只用于描述当前实现的数据形状、模块关系、调用顺序、管线和分支逻辑。
- 不要逐项复述当前组件树或内部结构图。

使用以下表达：

- “Gateway 使用 WebSocket 与前端通信。连接建立后进入 landing phase。”
- “三层依赖方向为 shared ← modules ← features。禁止下层反向依赖上层。”
- “保存配置后热重载 Gateway。不要重启进程。”

不要使用以下表达：

- “`useAvailablePort` 调用 `find_available_port` Rust 命令。”
- “`LandingPage` 接收 `theme` 和 `onComplete` 两个 props。”
- “pool 通过版本计数器 `bump()` 触发 React 重渲染。”

## 校验规则变更

- 变更长期规则前，按需查阅 Git 提交、diff 和讨论。
- 仅作校验。不要落地提交、历史或证据清单。
- 发现冲突或影响时，只在当前对话说明。等待确认。
- 确认后只更新当前结论。删除失效描述。不要保留演变记录。
- 证据不足或冲突时，不要猜测，不要落地。请求确认。

## 人工验收

- 更新人工验收通过的文档前，提交拟改内容。等待人工确认。
- 未经确认，不要自动更新。

## 审查入口

- 审查文档时，加载 `references/review.md`。
