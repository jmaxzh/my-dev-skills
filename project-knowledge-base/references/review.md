# 文档审查流程与注意事项

## 锁定范围

按入口锁定范围。

### 指定 docs 根目录

- 审查目录内全部 Markdown 文档。
- 不要扩大或缩小范围。

### 指定文档

- 仅审查指定文档。
- 按需读取直接相关文档作为证据。
- 不要把证据文档纳入本批范围。

### 根据代码变更反查文档

1. 从 commit、diff 或变更范围提取接口、命令、配置、环境变量、行为、路径、数据结构、错误码和用户流程。
2. 按“直接引用变更对象 → 描述其行为 → 描述其上层流程”定位文档。
3. 标记“已确认相关”“未确认相关性”或“明确无关”。
4. 仅将“已确认相关”纳入审查。

## 建立声明清单

1. 提取可验证声明。
2. 标记事实类型。
3. 确定规范性拥有者。
4. 定位权威源。
5. 检查重复定义。
6. 无法确定权威源时，标记“权威源未确定”。不要直接判错。

按事实类型查找规范性拥有者：

- 为产品或业务行为查找产品规范或业务规则。
- 为 API 契约查找 OpenAPI、Schema 或协议规范。
- 为 CLI 查找 CLI 规范或参数定义。
- 为配置查找配置 Schema 或配置规范。
- 为数据结构查找 Schema、Migration 或协议。
- 为实现结构和执行行为查找代码。
- 为部署查找 IaC 或部署配置。
- 为外部协议查找官方标准或第三方规范。
- 为说明性内容查找对应规范性事实源。

按以下顺序定位权威源：

1. 查找明确规范或契约。
2. 查找实际约束或执行源。
3. 查找说明性文档。

## 判定相关性

1. 判断变更是否影响文档声明的稳定事实。
2. 标记“已确认相关”“未确认相关性”或“明确无关”。
3. 无法证明相关性时，保留“未确认相关性”。不要直接判错。
4. 仅校验“已确认相关”的声明。

## 校验声明

1. 核对定义。
2. 核对默认值。
3. 核对取值范围。
4. 核对作用对象。
5. 核对生效条件。
6. 核对行为。
7. 核对边界条件。
8. 按 `SKILL.md` 校验目标读者、文档职责、命名、组织、格式和内容边界。
9. 完成验证后，标记“通过”或具体问题。
10. 尚未完成验证时，标记“未验证”。
11. 缺少关键证据时，标记“待确认”。不要直接判错。

## 处理越界内容

发现不应进入文档的实现细节时：

1. 停止比较新旧实现值。
2. 建议删除、抽象或改为引用。
3. 不要要求实现迁就错误文档。

发现访谈、对话、Plan、评审、Git 提交、diff、历史、弃选方案、推导或决策演变时：

1. 仅作证据。不要当作项目知识。
2. 只提炼当前、可复用的规则。
3. 删除其余内容。不要转存为决策记录、ADR、评审文档、Plan 或其他文件。
4. 不要新建页面保存参考。

## 输出结果

- 仅在当前对话输出审查结果。不要落地过程与证据。
- 列出审查范围。
- 列出规范性拥有者和权威源。
- 列出问题、证据和建议。
- 区分已确认问题、待确认项、未验证项和未确认相关性。
- 不要把范围外文档计入本批结论。

## 分批审查

- 每批审查 2～3 篇。
- 输出本批结果。
- 暂停并等待用户确认。
- 未经确认，不要继续下一批。
- 将已审文档作为后续批次的交叉证据。保留原审查结论。

## 注意事项

- 不要按文件名判断权威性。
- 不要把“存在对应实现”视为“文档正确”。
- 存在上层规范时，不要自动把代码或普通文档视为权威源。
- 无法确认时，标记“待确认”或“未确认相关性”。不要猜测。
- 发现重复定义时，保留规范性定义。将其他内容改为引用、派生说明、示例或验证证据。
- 不要为完成审查而扩大范围。
