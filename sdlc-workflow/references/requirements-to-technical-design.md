# 需求转技术方案

## 约束

1. 读取已确认需求、相关代码与现有文档。锁定目标、范围、非目标、约束、待决项。
2. 用户仅要求技术方案时，只生成技术方案。用户要求继续时，按其要求推进其他阶段。
3. 涉及旧有逻辑或存量数据：遵循用户确认的兼容策略；设计兼容、迁移、回滚。策略缺失或成本过高：提供简化迁移、限期兼容、废弃、破坏性变更选项；询问用户。禁止因兼容引入巨量复杂度。

## 先识别分层与变更边界

1. 先识别底层数据、底层架构、上层应用。按实际职责判断。禁止按目录名、类名或框架名机械划分。
2. 把数据模型、存储、接口契约、事件与状态生命周期归入底层数据。把领域核心、共享能力、基础服务与稳定扩展点归入底层架构。把界面、交互状态、应用用例与流程编排归入上层应用。
3. 判断需求是否修改底层数据或底层架构。不修改：说明依据。要修改：列出内容、原因、影响、兼容与迁移、替代方案；请求用户确认。
4. 未获确认：标记待决。不得把底层修改写成确定方案。不得实施。

## 分离底层与上层

1. 让上层依赖底层稳定接口。禁止底层感知界面与应用流程。
2. 采用类 MVVM 分工。分离展示、交互状态、应用编排、领域与数据。避免 Controller 混合流程、业务状态与数据访问。按职责判断。禁止只因名称否定 Controller。
3. 保持底层抽象简单、清晰、稳定、少而精。优先复用现有抽象。只抽象稳定、通用、必要的能力。
4. 禁止过度分层、提前抽象、一次性抽象。避免多余接口、适配器、工厂、包装与过长调用链。能用一个清晰模型解决时，不拆成多个中间层。

## 确认边界后设计数据结构

1. 先探索现有数据结构：实体、字段、类型、关系、约束、索引、状态、生命周期、接口契约、事件结构。
2. 再设计目标数据结构：新增与变更、所有权、不变量、读写路径、一致性、并发、迁移、兼容、容量。
3. 用数据结构约束流程、接口与模块边界。禁止先定流程、后补数据模型。
4. 无持久化数据变更时，检查内存状态、请求响应、消息与前端状态；说明无需变更的理由。

## 按顺序取证

1. 优先检索当前项目的类似需求、实现、设计文档与演进记录。引用文件路径、符号或提交证据。
2. 证据不足时，检索相同技术栈的著名高星开源项目。核验项目活跃度、相关实现与适用边界。引用仓库与具体位置。
3. 仍不足时，检索任意技术栈的著名高星开源项目。只提炼跨技术栈成立的领域模型、边界与权衡。
4. 最后检索业界权威资料、标准或文档。引用原始来源。
5. 记录采用与不采用的参考。说明差异、适用条件与取舍。禁止照搬。
6. 涉及 API、配置、运行时行为或技术栈规范时，查阅官方文档；以官方文档校验事实。仅采用官方规范或公认最佳实践。禁止臆造模式、API、配置与反模式。

## 在正确层级设计

1. 定位所属领域、架构层次、模块与责任边界。
2. 在根因或核心抽象处实现功能或修复。复用现有扩展点与领域能力。
3. 禁止使用外围特判、静默 fallback、重复逻辑、临时适配层或补丁绕过核心问题。
4. 发现现有抽象错误时，说明用户影响、根因、最小正确改动与迁移代价。请求用户决定超出需求范围的重构。

## 修改与问题表达

1. 修改现有文档时，保留原结构与有效信息。只修改冲突内容。禁止借机重构全文。
2. 发现问题时，先写用户影响；再写技术原因；最后写改进建议。
3. 完成自检：删除函数名、类名与技术术语后，仍能看懂问题为何影响用户。不能看懂时，重写。
