# 根据需求生成技术方案

## 约束

1. 按用户允许的证据范围读取已确认需求、相关代码与现有文档。锁定目标、范围、非目标、约束、待决项。用户禁止参考代码时，禁止读取代码；说明模块级改动与影响，不断言实际文件改动、现有实现缺口或准确工作量。将此证据范围约束应用于后续取证与设计。
2. 用户仅要求技术方案时，只生成技术方案。用户要求继续时，按其要求推进其他阶段。
3. 涉及旧有逻辑或存量数据：遵循用户确认的兼容策略；设计兼容、迁移、回滚。策略缺失时，依据现有契约与用户目标判断。无法合理推断或成本过高时，按需提供简化迁移、限期兼容、废弃、破坏性变更选项及代价；按“检查前置条件”第 5 条处理待决项。禁止因兼容引入巨量复杂度。

## 先判断可行性

1. 从目标、必要条件和约束出发，判断需求能否完整实现。
2. 区分原理上不可实现、约束不能同时满足、技术可行但代价过高、证据不足。禁止仅以复杂度高判定不可实现；禁止将证据不足判定为可行或不可行。
3. 存在冲突时，说明冲突条件、影响功能、可选取舍与代价。依据已知约束评估代价；缺少依据时标明不确定性。
4. 明确保证范围与失败边界。禁止把有条件保证表述为绝对保证。
5. 无法完整实现或存在需要用户决定的重大取舍时，交付判断与选项；按“检查前置条件”第 5 条处理待决项，推进后续设计。

## 检查前置条件

1. 检查需求规则、外部依赖、权限、环境、信息与兼容策略是否足以支撑可靠设计。禁止要求所有实施细节预先确定。
2. 区分阻塞设计的缺口、实施时需满足的条件、可由技术方案解决的问题。
3. 复用已知事实；只补查影响结论的缺失或冲突信息。
4. 不把接口设计、模块划分等常规技术决策作为用户必须补齐的前置条件。
5. 处理待决项：已有事实、契约和用户决策足以合理推断时，直接继续设计。关键缺口无法合理推断时，说明缺失信息、影响范围与决策方；提出必要澄清。仅暂停依赖该决定的设计；继续不受影响的部分。禁止将待决内容写成确定结论。仅当缺口阻塞整体设计时，暂停整体设计；交付阻塞原因、选项与下一步。
6. 可行且前置足够时，直接继续生成方案；不要逐阶段请求确认。已有适用结论时直接复用；遵循用户明确指定的范围、顺序与深度。

## 先识别分层与变更边界

1. 识别与本次需求相关的现有架构、职责边界与依赖关系。
2. 按需分析领域逻辑、应用编排、界面交互与基础设施等职责。确定接口契约、事件与状态的职责归属；不要统一归入数据层。
3. 判断需求是否修改数据模型或架构边界。不修改：说明依据。要修改：列出内容、原因、影响、兼容与迁移、替代方案。仅对超出授权范围、改变需求或存在重大代价的取舍请求确认；不要仅因涉及数据模型或架构边界而暂停。
4. 对需要确认且尚未确认的取舍，标记待决；不得写成确定方案或实施。复用用户已有确认，不重复询问。

## 按职责设计架构与分层

1. 按需求复杂度与现有架构划定职责边界、分层与依赖方向；沿用合理的现有分层。保持业务规则与界面、存储等具体实现解耦。以实际职责与依赖关系判断；不要按目录、命名、模式名称或固定层数划分，不要求每类职责独立成层。
2. 按项目特点选择架构模式。将 MVVM（模型—视图—视图模型）仅作为界面应用的分工示例；按需参考，分离展示、交互状态与业务数据。禁止将 MVVM 作为通用要求。
3. 按“优先复用成熟方案”复用适用的现有抽象。仅为当前需求的职责边界、业务不变量、依赖隔离或验证需要引入抽象；不要仅凭使用次数判断必要性，不为假设中的未来需求、复用或模块数量增加结构。没有独立职责边界时，采用单模块方案；仅在影响用户判断时说明取舍。

## 模块化技术方案

1. 按已划定的职责边界组织技术方案；说明各模块的输入、输出与依赖。
2. 在同一设计视图内，保持模块描述粒度一致：使模块职责范围与细节程度可比较。按需并列描述领域模块、基础设施模块与界面模块；说明依赖关系。避免将模块整体与其他模块的内部实现细节列为同级模块。
3. 通过清晰、稳定的接口协作。
4. 检查模块职责交叉、重复与隐式耦合；合并重复职责。
5. 设计模块前，按“优先复用成熟方案”核对现有能力。

## 协同设计数据结构、流程与模块边界

1. 探索相关现有数据结构：实体、字段、类型、关系、约束、索引、状态、生命周期、接口契约、事件结构。
2. 设计目标数据结构：新增与变更、所有权、不变量、读写路径、一致性、并发、迁移、兼容、容量。
3. 按任务需要选择设计切入点；迭代校验关键流程、数据结构、接口契约、模块边界、依赖方向与生命周期的一致性。定稿时，确保关键流程具备必要的数据结构与约束支撑。
4. 无持久化数据变更时，检查内存状态、请求响应、消息与前端状态；说明无需变更的理由。

## 优先复用成熟方案

1. 按优先级选择方案参考：项目中适用的既有方案 → 同场景、同技术栈的业界成熟方案 → 同场景、跨技术栈的业界成熟方案。以实际应用、可核验实现和明确适用边界界定“成熟方案”；禁止以星数代替适用性判断。
2. 先检索项目现有抽象、模块、接口、实现与扩展点；核对职责、语义、依赖方向及约束。适用时复用；不适用时，再参考外部方案。为关键新增或替代决策说明缺口与取舍。新增设计时，优先沿用项目既有风格与约定。避免复制已有逻辑；避免为复用引入职责混杂、反向依赖或多余抽象。
3. 按需逐级扩大参考范围。已有参考足以支撑关键设计决策时，停止扩展检索；不要遍历全部层级。
4. 采用外部参考方案前，核对关键场景、约束与依赖。优先直接复用适用部分；存在差异时，采用必要适配；仍不能满足时，设计新增部分。
5. 涉及 API、配置、运行时行为或技术栈规范时，直接查阅对应版本的官方资料，校验候选方案；不要受方案参考优先级限制。引用原始来源；禁止臆造 API、配置或技术事实。
6. 为关键设计决策标明参考来源、复用部分与必要差异；关联已述缺口与取舍，避免重复论证。引用项目文件路径、符号或提交证据；引用外部仓库与具体位置或原始资料。仅说明影响关键决策的未采用参考及理由。跨技术栈参考只提炼跨技术栈成立的领域模型、边界与权衡。标明未验证新增设计的假设与验证方式。

## 在正确层级设计

1. 在所属职责或核心抽象处实现功能。修复时，遵循[意图 → 需求](intent-to-requirements.md)中的修复目标与变更约束；默认优先根治，在根因或核心抽象处修复。避免无关改动。
2. 禁止将绕过根因的方案表述为根治。用户明确要求紧急止血，或已知时间约束不足以完成根治及必要验证时，优先止血；允许临时隔离、适配或局部修补。限制变更范围与影响范围，降低回归风险；验证受影响行为与需保持不变的关键行为。说明残留问题、回滚方式与后续根治事项。
3. 发现现有抽象错误时，说明用户影响、根因、最小正确改动与迁移代价。仅对超出授权范围或需要用户决定的重大取舍请求确认。

## 按层次交付

1. 先简述可行性与前置条件结论。存在待决项时，按“检查前置条件”第 5 条处理并交付；明确已确定内容、待决内容及下一步。
2. 条件满足时，默认交付高层技术方案、必要改动点及影响。
3. 用高层方案说明核心思路、模块职责、依赖与关键流程。
4. 用改动点说明修改对象、原因与范围；用影响说明行为、数据、兼容性与主要代价。
5. 按用户要求展开详细设计；不要默认堆叠字段、接口签名、状态机和实现细节。
6. 区分分析所需深度与交付所需篇幅。保留必要取证、数据结构与边界分析；只呈现支撑用户判断的内容。
